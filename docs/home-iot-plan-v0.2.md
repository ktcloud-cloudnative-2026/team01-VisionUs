# 가정 전자기기 IoT 연동 시스템 기획서

## 1. 프로젝트 개요

가정 내 전자기기를 하나의 시스템에서 연동·제어·모니터링하는 IoT 플랫폼을 마이크로서비스 아키텍처(MSA)로 구현하는 프로젝트입니다. 사용자는 웹 대시보드에서 기기 상태를 확인하고 원격으로 제어할 수 있으며, 각 기능은 독립된 서비스로 분리하여 확장성과 유지보수성을 확보합니다.

## 2. 해결할 문제

가정 내 전자기기가 기기별로 따로 제어되어, 사용자는 같은 불편을 반복해서 겪습니다.

| 누가                            | 어떤 불편을 겪나                                                            | 이 시스템의 해결 방향                     |
|---------------------------------|-----------------------------------------------------------------------------|-------------------------------------------|
| 가전을 여러 대 쓰는 가정 사용자 | 기기마다 별도 앱이나 리모컨을 써야 해서 전체 상태를 한눈에 볼 수 없음       | 하나의 웹 대시보드에서 통합 모니터링·제어 |
| 외출 중인 사용자                | 집을 나온 뒤 기기가 켜져 있는지 확인하거나 끌 방법이 없음                   | 웹 기반 원격 제어와 실시간 상태 확인      |
| 가족 구성원                     | 기기별 접근 권한을 나눌 수 없어 계정을 공유하거나 누구나 모든 기기를 조작함 | JWT 인증과 사용자별 기기 접근 권한        |

## 3. 목표

- 여러 가전 기기를 하나의 웹 인터페이스에서 통합 관리

- 기기 상태 데이터의 실시간 수집 및 이력 저장

- 서비스 단위 분리를 통한 독립 개발·배포·확장

- 안전한 사용자 인증과 기기 접근 제어

## 4. 성공 기준

정상 사용 시나리오(올바른 요청으로 구성한 REST API 요청)를 측정 대상으로 합니다.

### 4.1 응답 코드 기준

4xx는 잘못된 요청을 올바르게 거부한 경우도 포함하므로, 일부러 보낸 잘못된 요청(보안 테스트 등)은 측정에서 제외합니다.

| 구분 | 기준      | 의미                                                 |
|------|-----------|------------------------------------------------------|
| 2xx  | 98% 이상  | 성공                                                 |
| 4xx  | 1.5% 이하 | 올바른 요청인데 4xx가 나온다면 시스템 또는 연동 결함 |
| 5xx  | 0.5% 이하 | 서버 결함                                            |

세 값의 합은 98% + 1.5% + 0.5% = 100%입니다.

### 4.2 속도 기준

속도는 평균이 아니라 백분위로 정합니다. "95%가 500ms 이내"는 전체 요청을 빠른 순으로 세웠을 때 95%가 500ms 안에 끝난다는 뜻입니다.

| 항목                   | 기준                      | 비고                          |
|------------------------|---------------------------|-------------------------------|
| 일반 REST API 응답     | 95%가 500ms 이내          | 요구사항 정의서 NFR-02와 동일 |
| 제어 명령 후 기기 반영 | 평균 1초 이내 (로컬 환경) | 요구사항 정의서 NFR-01과 동일 |

## 5. 주요 기능

### 5.1 기기 관리

- 기기 등록, 수정, 삭제 및 그룹(방/구역) 관리

- 기기 유형별 속성 정의 (조명, 에어컨, 공기청정기, 등)

### 5.2 실시간 상태 모니터링

- 기기 온라인/오프라인 상태 및 센서 값 실시간 표시

- 상태 변경 이벤트 수신 및 대시보드 반영

### 5.3 원격 제어

- 전원, 모드, 설정값 등 제어 명령 전송

- 명령 실행 결과 및 응답 확인

### 5.4 이력 및 통계

- 기기 상태·제어 이력 저장 및 조회

- 기간별 사용 패턴 및 센서 데이터 통계

### 5.5 사용자 인증·권한

- 회원가입/로그인, JWT 기반 인증

- 사용자별 기기 접근 권한 관리

## 6. 기술 스택

| 영역          | 기술                           |
|---------------|--------------------------------|
| 프론트엔드    | Next.js                        |
| 백엔드        | Node.js (Express)              |

| API           | REST API                       |
| 인증          | JWT                            |

## 7. 시스템 아키텍처

### 7.1 구성 요소

- **웹 클라이언트(Next.js)**: 대시보드 및 제어 UI

- **API 게이트웨이/서비스(Express)**: REST API 제공, JWT 검증, 서비스 간 라우팅

- **마이크로서비스**: 사용자·인증 서비스, 기기 관리 서비스, 상태 수집(텔레메트리) 서비스, 제어 명령 서비스

- **MQTT 브로커**: 기기(시뮬레이터)와 서비스 간 메시지 중계

- **PostgreSQL**: 사용자, 기기, 상태 이력 데이터 저장

- **가전 기기 시뮬레이터**: 실제 가전 대신 가상 기기를 구동하여 상태 발행 및 명령 수신

### 7.2 데이터 흐름

1.  시뮬레이터가 MQTT 토픽으로 상태 데이터를 발행합니다.

2.  상태 수집 서비스가 이를 구독하여 PostgreSQL에 저장하고 클라이언트에 전달합니다.

3.  사용자가 웹에서 제어 요청을 보내면 REST API가 JWT를 검증한 뒤 제어 서비스로 전달합니다.

4.  제어 서비스가 MQTT 명령 토픽으로 발행하고, 시뮬레이터가 실행 후 결과를 응답합니다.

### 7.3 MQTT 토픽 구조(안)

- 상태 발행: `home/{deviceId}/status`

- 제어 명령: `home/{deviceId}/command`

- 명령 응답: `home/{deviceId}/response`

## 8. 서비스 구성

| 서비스            | 역할                            |
|-------------------|---------------------------------|
| 인증 서비스       | 회원가입, 로그인, JWT 발급·검증 |
| 기기 서비스       | 기기·그룹 CRUD, 소유자 관리     |
| 텔레메트리 서비스 | MQTT 상태 구독, 이력 저장, 조회 |
| 제어 서비스       | 제어 명령 발행, 응답 처리       |
| 프론트엔드        | 대시보드, 제어 화면, 이력 조회  |

## 9. 데이터 모델(초안)

- **users**: `id, email, password_hash, created_at`

- **devices**: `id, user_id, name, type, group, created_at`

- **device_status**: `id, device_id, payload(JSON), recorded_at`

- **commands**: `id, device_id, command, result, issued_at`

## 10. 보안 고려사항

- 비밀번호 해시 저장, JWT 만료 시간 및 갱신 정책 설정

- 기기별 소유자 검증을 통한 접근 제어

- MQTT 브로커 인증 및 토픽 단위 접근 제한

- API 입력값 검증 및 요청 제한(rate limiting)
